## Proposed Architecture

```mermaid
graph LR
    subgraph "shared-lib"
        POLICY["oss-call-policy.json<br/>(NEW — operation-keyed<br/>timeoutMs/maxRetries)"]
        OSC["ossStructuredCall<br/>(oss-structured-output.mjs)<br/>+ heartbeat timer<br/>+ operation resolution<br/>+ category passthrough"]
        CLE["classifyLlmError<br/>(robustness.mjs)<br/>— unchanged, reused"]
    end
    subgraph "audit-orchestration"
        S1["validatedTriagerCall<br/>(tiered-pipeline.mjs)<br/>operation: stage1_triage"]
        DISC["glmCall<br/>(tiered-pipeline.mjs)<br/>operation: discovery_generation"]
        OUTER["runShadowTieredPipeline<br/>(tiered-shadow-compare.mjs)<br/>outer 20-min race — reconciled"]
    end
    POLICY -->|resolves timeoutMs/maxRetries by operation| OSC
    OSC -->|classifyLlmError(err)| CLE
    CLE -->|category, now returned not discarded| OSC
    S1 -->|operation label| OSC
    DISC -->|operation label| OSC
    S1 --> OUTER
    DISC --> OUTER
```

**Data flow**: a call site names its semantic `operation` (`stage1_triage` | `discovery_generation`); `ossStructuredCall` resolves `timeoutMs`/`maxRetries` from the committed policy config (falling back to today's hardcoded defaults when `operation` is omitted — dormant callers 3/4/5 above are unaffected). While a request is in flight, a heartbeat timer (independent of the existing abort timer) logs elapsed progress. On terminal failure, the already-computed `classifyLlmError` category is now included in the return value, so `discovery-portfolio.mjs`'s thrown error message and `tiered-shadow-log.jsonl`'s `tieredFallbackReason` can carry it forward for future diagnosis without a live repro.

**Key design decisions**:
- **Reuse, don't duplicate, error classification** (#5 Single Source of Truth) — extend what `classifyLlmError` already returns into the caller-visible contract, rather than the parallel taxonomies both brainstorm models proposed.
- **Operation-keyed, not model-keyed, policy** (#4 No Hardcoding + #3 Modularity) — reconciles the brainstorm's GPT-vs-Gemini disagreement: call sites stay simple (name an operation), the actual numbers live in one reviewable file, and it never needs updating just because a new model is swapped in (the stated future need — testing more OpenRouter models).
- **Optional `operation` param, default preserves today's behaviour exactly** (#18 Backward Compat) — the 3 dormant/frozen call sites (audit-shadow.mjs, solo-control-audit.mjs, cheap-triager-validate.mjs) require zero changes and zero behavior change.
- **Heartbeat only, no streaming, no circuit breaker** — both explicitly considered and rejected in the brainstorm as disproportionate machinery for a low-frequency batch pipeline; heartbeat logging alone resolves the actual reported symptom (silence during a live call).

## Execution Model

**Dependency chain identified** (Phase 1.5): the two call-site changes (tiered-pipeline.mjs) cannot be written correctly until the wrapper's new contract (what `operation` resolves to, what fields the return shape gains) is decided and implemented — a real sequential dependency, not an artificial one. This is reflected in phase ordering below (§7b), but is **not** split into separately-gated §11 clusters: the wrapper change and its call-site wiring must be read together to verify correctness (a reviewer auditing "wire the call sites" needs full context of the wrapper's new contract anyway), so splitting them into two audit gates would add ceremony without adding review value. One cohesive union diff, audited once.

**Worst-case latency reconciliation against the outer 20-minute race** (the concrete numeric check §6 of the incident report demanded, revised per round-1 audit H1). The precise per-candidate worst case includes the retry backoff, not just `timeoutMs × attempts`: `ossStructuredCall`'s retry delay is `800ms × (attempt + 1)` between attempts (`oss-structured-output.mjs:~262`), so for `stage1_triage` (45s timeout, 1 retry): `45000×2 + 800×1 = 90800ms (~90.8s)` per candidate, not a flat 90s. Discovery generation (GLM ∥ Sonnet via `Promise.all`) costs up to `120s × 2 attempts + 800ms backoff = 240.8s` (bounded by the slower of the two; this plan only touches GLM's budget). Stage 0 is deterministic (negligible).

**Round-1 audit finding H1 (compromise ruling)**: a comment alone does not reconcile the budgets — the plan's own math already showed the outer race CAN be exceeded for candidate counts above ~8-10, silently. GPT's proposed fix (full deadline/cancellation-context propagation through Stage 1 → discovery → Stage 2 → `ossStructuredCall`) was accepted as too large for this incident's scope; the compromise is a **bounded, observable Stage-1 admission guard** — proportionate (one new config value + a loop check in the existing sequential loop), not a new cancellation architecture:

- **`oss-call-policy.json` gains a `stage1TriageBudget.totalMs` field** (proposed: `600000` = 10 min) — a documented, evidence-based reservation for the *entire* sequential Stage-1 loop, leaving the remaining ~10 min of the 20-min outer race for discovery (240.8s) + Stage 2's Gemini adjudication + overhead.
- **`stage1-triage.mjs`'s `runStage1CheapTriage` loop** records `loopStartMs = Date.now()` before iterating. Before calling `triagerCall` for each envelope, it computes that candidate's worst-case duration from the resolved `stage1_triage` policy (`timeoutMs × (maxRetries+1) + backoff sum`) and admits the call only if `(Date.now() - loopStartMs) + worstCaseMs <= stage1TriageBudget.totalMs`. If not, it stops the loop and marks every **remaining, not-yet-started** envelope with a distinct structured status `skipped-budget-exhausted` — explicitly represented, never silently discarded, and never conflated with a real provider/triager failure (a different status than `mechanical_dismissed` or a classified error).
- **Result/log propagation**: the Stage-1 result object gains a `skippedBudgetExhaustedCount` (and the skipped envelope IDs) so `tiered-shadow-log.jsonl` and the tiered result envelope can distinguish "ran out of admission budget" from "the model failed" — an operator seeing this in telemetry has the evidence needed to reconsider `stage1TriageBudget.totalMs` or (per the revisit trigger below) prioritize parallelizing Stage 1.
- This closes the specific gap H1 identified (an unbounded final Stage-1 call blowing past the 20-min race with no visibility) **without** touching `ossStructuredCall`'s signature, without new cancellation semantics, and without changing discovery or Stage 2 at all.

**Deferred as independent, pre-existing debt (per H1's ruling, not silently dropped)**: `Promise.race` (used by `runShadowTieredPipeline`'s outer 20-min race) does not cancel its losing promise — an inner OpenRouter call can keep running (and spending) after the outer race has already recorded a timeout. This property is identical before and after this plan; fixing it requires threading an `AbortSignal`/cancellation context through the entire inner pipeline (Stage 1 → discovery → Stage 2 → `ossStructuredCall`), a materially larger and architecturally different change than this plan's heartbeat/policy/admission-guard scope. **Not represented as solved by the new admission guard** — the guard bounds how much NEW work Stage 1 can *start*, it does not cancel work already in flight. Tracked as a follow-up, alongside the Stage-1-parallelization revisit trigger below.

Parallelizing Stage 1 (removing the sequential-loop multiplier entirely) remains explicitly **out of scope** for this plan (right-sizing — a larger, independent change than fixing today's silence-during-a-hang incident) and is the concrete revisit trigger below.

## Sustainability Notes

**Right-sizing** (band-aid / over-engineered / chosen):
- **Band-aid**: bump `timeoutMs` down globally for `ossStructuredCall` and call it done. Leaves the silence-during-a-live-call problem unsolved for any future long-running operation, and a global timeout is provably wrong for two call sites with very different latency profiles (today's actual root cause).
- **Over-engineered**: a circuit breaker + per-`(model, provider, operation)` timeout matrix + streaming-as-heartbeat. Explicitly rejected in the brainstorm — this is a low-frequency batch audit pipeline, not a live service; a breaker adds state/failure-modes disproportionate to the problem, and a model-keyed matrix is a maintenance burden that will constantly be stale as new OpenRouter models are tested.
- **Chosen**: an operation-keyed (not model-keyed) policy config + heartbeat logging + category passthrough via the *existing* classifier. Serves the current requirement (two known call sites with different latency needs, today) without inventing infrastructure for hypothetical futures (streaming, breakers) the brainstorm already ruled out.

**Assumptions that could change**: the assumption that Stage 1's sequential per-candidate loop stays a small-N operation (documented above, not silently assumed) — if candidate volume grows, this plan's admission guard will start producing `skipped_budget_exhausted` candidates rather than silently exceeding the outer race, but parallelizing Stage 1 is still the real fix at that point, not a bigger budget reservation. **Revisit trigger**: if `skippedBudgetExhaustedCount > 0` appears routinely in `tiered-shadow-log.jsonl` (the admission guard is now the concrete, machine-readable signal — no longer just heartbeat-log inference), or if the outer 20-minute race fires with `fallbackReason` indicating an in-progress (not-yet-failed) inner call (the deferred `Promise.race`-cancellation gap), escalate to parallelizing Stage 1 as a follow-up plan.

**Extension points deliberately built in**: the policy config is additive — a future third operation (e.g. `adjudicator_screen` if a Tier-C OSS adjudicator eval is ever run through this same wrapper) is one new JSON entry, not a code change.

## File-Level Plan

1. **`scripts/lib/oss-call-policy.mjs`** (create — new item, added per round-2 M1: policy resolution must be a single shared module, not duplicated between the wrapper and the admission guard)
   - Exports a small, immutable contract: `getOssOperationPolicy(operation)` (returns `{timeoutMs, maxRetries}` for a known operation, today's literal defaults `{timeoutMs: 300000, maxRetries: 2}` for `operation === undefined`, **throws** for an operation present but unrecognized — round-1 M2, see below), `getStage1TriageBudget()` (returns the `stage1TriageBudget.totalMs` value), `RETRY_BACKOFF_BASE_MS = 800` (a named export — the **single, real source of truth** for the retry-backoff constant, round-3 M2 fix: item 2's retry-loop delay line imports and uses this EXACT exported symbol instead of keeping its own literal `800`, so there are not two numbers that merely happen to match — a future change to one automatically changes the other), and `calculateWorstCaseAttemptDuration(policy)` (`timeoutMs × (maxRetries+1) + RETRY_BACKOFF_BASE_MS × sum(1..maxRetries)`, built from the same exported constant).
   - **File loading is injectable, not a bare singleton** (round-2 M2): `createOssCallPolicyResolver({ readFile = fs.readFileSync } = {})` is the factory; it resolves `oss-call-policy.json` via a module-relative URL, parses + schema-validates **once** on first use, and caches the result on the resolver instance. Production code uses one module-scope default instance (`createOssCallPolicyResolver()`, called once, its exported functions bound to it) — the SAME cached-once behavior as before — while tests can construct a fresh instance with a fake `readFile` to exercise the malformed-policy-at-first-use path without mutating the committed file or fighting a shared cache. The schema enforces `version` (known literal), per-operation `timeoutMs` (finite positive integer) / `maxRetries` (non-negative integer, upper bound ≤3), and `stage1TriageBudget.totalMs` (finite positive integer). A malformed file throws a diagnostic naming the config path and the invalid field at first use — fails deterministically, never silently falls back for a *known-but-malformed* entry.
   - **Omitted vs. unrecognized `operation` are NOT the same** (round-1 M2): `operation === undefined` → today's literal defaults, byte-identical for the 3 dormant/frozen callers. `operation` **present but not a key in the policy** → `getOssOperationPolicy` throws immediately (before any network call) with a clear configuration/programming-error message naming the unrecognized operation — a silent fallback would silently reintroduce today's 15-minute incident for a newly-wired call site with zero test/runtime signal.
   - **Why this file**: single source of truth for policy resolution AND worst-case-duration math, consumed by `oss-structured-output.mjs` (item 2), `tiered-pipeline.mjs` (item 4, resolving the admission budget it owns), and `stage1-triage.mjs` (item 7) — closes round-2 M1's DRY/drift risk directly, rather than each caller independently reimplementing the backoff formula.

   - **Retry-delay line now imports item 1's `RETRY_BACKOFF_BASE_MS`** (round-3 M2): the existing `const delayMs = 800 * (attempt + 1);` becomes `const delayMs = RETRY_BACKOFF_BASE_MS * (attempt + 1);` — the literal `800` is deleted from this file entirely, not just documented as matching. One symbol, one place it can drift from.

## Risk & Trade-off Register

- **Trade-off**: shortening `discovery_generation`'s timeout from the implicit 300s to 120s could, in principle, fail a genuinely slow-but-healthy GLM call that previously would have succeeded within 300s. Mitigated by: (a) today's two successful `tieredRunStatus: "complete"` comparisons (2026-07-14, 18:43/18:49 UTC) completed in well under 120s total including discovery, so 120s is not aggressive against observed healthy behavior; (b) the heartbeat makes a genuinely-still-working call visible before it's killed, so an operator can raise the config value with evidence rather than guessing.
- **What could go wrong**: the sequential Stage-1 multiplication (Execution Model above) is now BOUNDED by the round-1/2/3 admission guard (a caller-owned budget; a candidate is only started if it fits; skipped candidates are excluded from Stage 2 rather than inflating it; classification is now typed and persisted end-to-end) rather than merely documented — but the underlying `Promise.race`-non-cancellation limitation (deferred, independent pre-existing debt) means in-flight work started just before exhaustion can still run past the point a later admission check would have refused it, and Stage 2's own duration remains unbounded (never in this plan's scope). Not eliminated, bounded.
- **Deliberately deferred**: streaming-as-heartbeat and a circuit breaker (both brainstorm proposals) — genuinely useful ONLY if OpenRouter instability recurs frequently or output sizes grow much larger; premature now (YAGNI — no current requirement forces either). Also deferred: `Promise.race` loser-cancellation for the outer 20-min race, and independently bounding Stage 2's own worst-case duration — both materially larger, independent changes than this plan's heartbeat/policy/admission-guard scope.
- **Plan-audit convergence note**: rounds 1-3 each surfaced concrete, code-traced gaps (not restated rigor pressure) — this is recorded honestly rather than silently stopping at a round cap. Round 3 is the deliberate stopping point: remaining implementation-precision questions (exact variable names, line numbers shifting during real implementation) are the kind `/audit-code` verifies against real code, the correct artifact for that level of detail — not further plan elaboration.
