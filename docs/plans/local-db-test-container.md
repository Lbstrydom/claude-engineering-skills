## 2. Proposed Architecture

```mermaid
sequenceDiagram
    participant Op as "Operator (npm run db:local)"
    participant CLI as "scripts/db-test-container.mjs"
    participant Doc as "Docker Desktop"
    participant PG as "pgvector pg16 @ 127.0.0.1:5433"
    participant Node as "child: node --test / setup-postgres"

    Op->>CLI: "mode: suites (default) / regen-schema / up / down"
    CLI->>Doc: "docker version (preflight - fail loud if absent)"
    CLI->>Doc: "reconcile: rm stopped ces-db-test only; running -> exit 3"
    CLI->>Doc: "docker run -d --name ces-db-test -e POSTGRES_PASSWORD -p 127.0.0.1:5433:5432"
    CLI->>PG: "pg Client connect poll (bounded retry, no sleep-guess)"
    CLI->>Node: "setup-postgres --migrate (env: AUDIT_DB_URL=container DSN)"
    CLI->>Node: "destructive suites (env: AUDIT_DB_TEST_URL=container DSN; AUDIT_DB_URL NOT injected)"
    Node->>PG: "DROP SCHEMA public CASCADE (assertDisposableDbUrl passes: loopback, not supabase)"
    CLI->>Doc: "docker rm -f -v ces-db-test (skipped with --keep; idempotent)"
    CLI-->>Op: "exit map 0/1/2/3/4 (never green without having run)"
```

**Component**: one new CLI, `scripts/db-test-container.mjs`, owning the whole
lifecycle: preflight → start → readiness → run target workload → teardown.

**Modes** (single positional or default):

| Mode | What it runs against the fresh container |
|---|---|
| `suites` (default) | Full CI mirror: `--migrate` → schema-diff verify → drift-justification test (own invocation) → `--test-concurrency=1` destructive trio → contract suite |
| `regen-schema` | `--migrate` → `generate-expected-schema.mjs --out tests/fixtures/expected-schema.json` |
| `up` | start + migrate + **keep running**; print both DSN forms for manual work |
| `down` | `docker rm -f` the named container (idempotent; exit 0 if absent) |

**Flags**: `--keep` (skip teardown after `suites`/`regen-schema`; prints the
`down` command), `--port <n>` (default 5433 — escape hatch for a conflict),
`--selfcheck-relocation` (prints `OK`, exits 0 — the repo-wide CLI smoke
contract; cheap to honour even though this script is not synced, and it
removes any ambiguity about whether the contract applies).

**Container invocation (exact argv — H1)**: the postgres image family
*refuses to initialize* an empty data directory without `POSTGRES_PASSWORD`;
all three env vars are explicit, mirroring CI's service block:

```
docker run -d --name ces-db-test \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=postgres \
  -p 127.0.0.1:<port>:5432 \
  pgvector/pgvector:pg16
```

(Local-only dummy credentials on a loopback-bound port — identical to CI's
throwaway values, never a real secret.)

**Step vectors (exact argv + env — H4)**: the `suites` sequence is a
data-driven `STEPS` array; each entry below is the literal `execFile`
invocation and its env additions (beyond inherited env). `<DSN>` =
`postgresql://postgres:postgres@127.0.0.1:<port>/postgres`.

| # | Step | argv (`execFile(file, args)`) | Env added |
|---|---|---|---|
| 1 | migrate | `node scripts/setup-postgres.mjs --migrate` | `AUDIT_DB_URL=<DSN>`, `AUDIT_DB_SSL_MODE=disable` |
| 2 | schema-diff verify | `node scripts/postgres-parity/generate-expected-schema.mjs --out <run-tmp>/live-schema.json`, then in-process `_internals.diffSchemas(expected-schema.json, live)` (same comparator CI uses; non-empty diff → step fails). `<run-tmp>` = a per-invocation `fs.mkdtempSync(path.join(os.tmpdir(), 'ces-db-test-'))`, removed best-effort in the same `finally` as teardown (R2-L1 — removal failure is logged, never affects exit code) | `AUDIT_DB_URL=<DSN>`, `AUDIT_DB_SSL_MODE=disable` |
| 3 | drift-justification (own invocation — needs intact schema; `node --test` sorts alphabetically, commit e084618) | `node --test tests/symbol-index-drift-justification.test.mjs` | `AUDIT_DB_TEST_URL=<DSN>`, `AUDIT_DB_SSL_MODE=disable` — **`AUDIT_DB_URL` deleted from inherited env** (Gemini-G2) |
| 4 | destructive suites | `node --test --test-concurrency=1 tests/db-date-parser.test.mjs tests/db-withtx.test.mjs tests/db-setup.test.mjs` | `AUDIT_DB_TEST_URL=<DSN>`, `AUDIT_DB_SSL_MODE=disable` — **`AUDIT_DB_URL` deleted from inherited env** (R3-H2; see env discipline) |
| 5 | contract suite | `node --test tests/learning-store-contract.test.mjs` | `AUDIT_DB_URL=<DSN>`, `AUDIT_DB_SSL_MODE=disable` |

`regen-schema` mode = step 1, then
`node scripts/postgres-parity/generate-expected-schema.mjs --out tests/fixtures/expected-schema.json`
(env as step 2).

**Key design decisions**:

- **Ephemeral per-invocation container, fixed name `ces-db-test`** (#13
  idempotency): every start is preceded by a **state-aware reconcile** (H2):
  `docker inspect` the name; if the container exists in a non-running state
  (`exited`/`created`/`dead`), remove it (stale from a crashed prior run);
  if it is **running**, fail loud (exit 3) with the message *"container
  ces-db-test is already running — another invocation may own it; run
  `npm run db:local down` if it's yours and idle"*. Never `rm -f` a running
  container implicitly — a concurrent invocation's live database is not
  "stale". (`up` follows the same rule; `down` is the only mode that removes
  a running container, and doing so is its explicit, operator-requested
  job.) **Ownership-scoped cleanup (R3-H1)**: the inspect→run pair is not
  atomic, so two invocations can race; Docker's name uniqueness makes
  exactly one `docker run` succeed. Ownership is therefore the **container
  ID printed by this invocation's own successful `docker run`** — teardown
  and the signal handler remove ONLY by that captured ID (`docker rm -f -v
  <id>`), never by name. An invocation whose `docker run` fails (lost the
  race, or any other cause) owns nothing: its cleanup paths are no-ops.
  **Run-failure classification (Gemini-G1 — never mask the real error)**:
  a failed `docker run`'s stderr is inspected — a name-conflict error
  (`is already in use by container`) exits 3 with the running-container
  message; a bind/port-allocation error exits 2 with the real stderr plus
  an explicit `--port` suggestion; anything else exits 2 with the real
  Docker stderr verbatim. Exit 3 is reserved for genuine name collisions —
  a port conflict must never be presented as a concurrency race. Only
  `down` operates by name, because removing whatever holds the name is its
  explicit job. No volume, no bind mount: state dies with
  the container, which is the point (Gemini's staleness argument: `DROP
  SCHEMA` can't reset roles/extensions; a fresh container matches CI's
  pristine env exactly). **Anonymous-volume hygiene (R2-H1)**: the postgres
  image family declares `VOLUME /var/lib/postgresql/data`, so a bare
  `docker rm -f` leaks an anonymous volume per container lifetime. Every
  removal path — teardown, `down`, stale-reconcile, signal handler — uses
  `docker rm -f -v ces-db-test` (`-v` removes the anonymous volume with the
  container). The integration smoke test asserts no `ces-db-test`-attached
  volume survives a full up/down cycle.
- **CI-parity constants are single exported values, guarded mechanically**
  (#8, #10; extended per M2 beyond just the image): the script exports
  `DB_TEST_IMAGE = 'pgvector/pgvector:pg16'`, `DESTRUCTIVE_SUITE_FILES`
  (the step-4 file list), `ISOLATED_SUITE_FILES`
  (`['tests/symbol-index-drift-justification.test.mjs']`), and
  `CONTRACT_SUITE_FILES`. The unit test asserts against
  `.github/workflows/postgres-parity.yml` that: (a) the workflow contains
  `DB_TEST_IMAGE` verbatim; (b) every file in each exported list appears in
  the workflow; (c) the workflow's destructive step contains
  `--test-concurrency=1`; and (d) — the reverse direction — every
  `tests/*.test.mjs` path referenced in the workflow's run steps appears in
  one of the exported lists (a NEW CI suite that the local mirror doesn't
  know about goes red, closing M2's "local run can't reveal an omitted CI
  step" gap). Argument-level or ordering drift beyond this is accepted
  residual risk, recorded in §8.
- **Readiness = TCP connect poll with the `pg` client from the host**
  (bounded: 500ms interval, 60s cap), not `docker exec pg_isready` and not
  `sleep N` (#12, #19). The official Postgres image runs a *temporary* server
  during initdb that `pg_isready` inside the container can see; only a
  successful host-side TCP connect on 5433 proves the real server is
  accepting. On timeout: fail loud with the last connect error, tear down.
- **Env discipline mirrors CI exactly** (#12 — the load-bearing subtlety):
  - migrate / schema-diff / regen / contract steps: child env gets
    `AUDIT_DB_URL=<container DSN>` + `AUDIT_DB_SSL_MODE=disable`. Setting it
    in the child env means `dotenv` will NOT override it (dotenv never
    overwrites existing keys) — the developer's real `.env` DSN is inert.
  - destructive-suite step: child env gets `AUDIT_DB_TEST_URL=<container DSN>`
    + `AUDIT_DB_SSL_MODE=disable`, and `AUDIT_DB_URL` is **actively deleted
    from the inherited env** (R3-H2 — not merely "not injected": an
    operator-exported `AUDIT_DB_URL` in the parent shell would otherwise be
    inherited, and if it happened to equal the container DSN the guard's
    equality check would false-positive). Deleting it reproduces CI's
    contract exactly: that step's env contains no `AUDIT_DB_URL` at all. If
    the developer's `.env` then loads the real production DSN *inside* the
    test process (dotenv fills only absent keys), that is the guard's
    *designed* contract (`productionUrl ≠ testUrl` → pass). Injecting the
    container DSN as `AUDIT_DB_URL` would false-positive the guard — the
    exact trap the CI workflow's comment documents. **The deletion rule
    follows the variable, not the step number (Gemini-G2)**: `buildStepEnv`
    deletes `AUDIT_DB_URL` from the inherited env for EVERY step that
    receives `AUDIT_DB_TEST_URL` (steps 3 and 4 — all destructive-guard
    consumers run in a uniform env). The unit test asserts the deletion for
    both steps with a deliberately polluted parent env.
- **Docker unavailable / container fails to start → loud non-zero exit**
  (#15, #16 deliberately inverted: for a safety tool, *crash* beats
  *degrade*). Per the pre-ship-empirical-verify doctrine's "audit your
  success paths": there is no code path that exits 0 without having run the
  requested workload. `docker version` preflight failure prints a hint
  (Docker Desktop not running; see the 2026-07-16 WSL-wedge recovery in
  memory) and exits 2.
- **Orchestrate, don't reimplement** (#1): migration, schema diff, fixture
  generation, and the test files themselves are invoked as child processes
  exactly as CI invokes them (`execFile`, no shell — Windows-safe). The CLI
  adds only what CI's YAML provides: container lifecycle + env assembly +
  step sequencing.
- **Exit code = first failing step's code; steps after a failure are
  skipped except teardown** (#15). Exit-code map: `0` success, `1` a step
  failed, `2` environment/preflight (Docker absent, image pull failed,
  readiness timeout), `3` container-name conflict (running container found),
  `4` workload succeeded but teardown failed (R2-H2 — never masks a green
  workload as fully-clean when the container may still exist). **Precedence
  (R2-H2)**: a workload failure always wins (teardown failure is then only
  logged — the operator's signal is the failing suite, and the leftover
  container is removed by the next invocation's reconcile or `down`);
  teardown-failure exit 4 applies only when the workload was green.
  Teardown is **idempotent via a `tornDown` flag** so the `finally` path and
  the signal handler cannot double-run it; the diagram's "worst child exit"
  phrasing is superseded by this map.
- **Lifecycle robustness (M1)** (#15, #16): teardown runs in a `finally`
  AND on `SIGINT`/`SIGTERM` — the handler kills the active child process
  (if any), runs `docker rm -f -v <owned-container-id>` (by the captured ID
  per the R3-H1 ownership rule — a no-op when this invocation never
  successfully created the container), and exits 130/143. All `docker` CLI invocations get a bounded timeout via
  `execFile`'s `timeout` option: 10s for `version`/`inspect`/`rm`, 120s for
  `run` (first-run image pull is separate: `docker pull` with inherited
  stdio and a 10-minute cap, so progress is visible and a stall is not
  infinite). Readiness poll: 500ms interval, 60s cap, teardown on timeout.
  Workload child steps get **no timeout** (suite duration is legitimate and
  variable) but are killed by the signal handler; a hung Docker daemon
  surfaces as the bounded docker-command timeout, not a silent hang — the
  CLI never attempts to repair Docker.
- **Not synced to consumers** (#5): this script exists for THIS repo's test
  suites and fixture; it is not added to the sync map. It still implements
  the 2-line `--selfcheck-relocation` handler (H3): the repo-wide CLI smoke
  contract is cheapest to satisfy uniformly, and honouring it costs less
  than defending the exemption. It is deliberately NOT added to
  `CLI_SMOKE_SET` (that CI guard enumerates *synced* CLIs whose relocation
  must be proven).

**Data flow (suites mode)**: operator → CLI parses mode/flags → docker
preflight → reconcile-remove stale container → `docker run -d` →
pg-connect poll → sequential child steps with per-step env (above) →
teardown → aggregate exit.

## 6. Sustainability Notes

**Right-sizing gate** (new structure: one CLI + one npm-script pair + a
parity-guard test):

- **Band-aid extreme**: a documented `docker run` one-liner in the runbook.
  Rejected: the env discipline (which var goes to which step) is the part
  humans will get wrong by hand — it's exactly what caused INC-002; and the
  image tag would drift from CI with no signal.
- **Over-engineered extreme**: `docker-compose.yml` + named volume +
  `up/down/reset` lifecycle scripts + generic multi-container config +
  consumer sync. Rejected: one container, one image, no inter-container
  wiring — compose adds a config surface with no current requirement;
  a persistent volume creates the staleness class the ephemeral design
  exists to kill.
- **Chosen**: single Node CLI, pinned constant, parity-guard test. Serves the
  two *current* requirements (run destructive suites locally; regenerate
  `expected-schema.json` locally) and nothing speculative.

**Manual vs scripted**: all-new files, no repetitive edits — by hand.

**Assumptions that could change**:
- CI moves off `pgvector/pgvector:pg16` → parity test goes red, one-constant
  fix (the designed seam).
- CI adds/reorders steps → the `suites` sequence drifts. Mitigated
  mechanically for the highest-value cases (M2): the parity test asserts
  image + both directions of test-file membership + the concurrency flag,
  so a NEW or REMOVED CI suite goes red locally. Residual (accepted, §8):
  argument-level and step-*ordering* drift within already-known files. The
  sequence lives in one `STEPS` array (data-driven, #20) so fixes are
  additive.
- Port 5433 collides with something → `--port` flag exists; DSN is derived
  from one place.

**Extension points deliberately built in**: mode dispatch table (a future
`psql` convenience mode slots in); `STEPS` array (a future golden-fixtures
step appends).

## Security Considerations (INC-002 crosses this plan's path)

INC-002 (2026-07-14 production wipe via `AUDIT_DB_TEST_URL` aliasing) is
`manual-verification-required` and its affected paths are exactly the suites
this plan makes runnable locally. Addressed invariants:

1. **The mitigation is not weakened**: `assertDisposableDbUrl` is not
   modified, wrapped, bypassed, or allowlisted. The container DSN passes the
   existing checks by construction (loopback host, never equal to a Supabase
   URL). The suites' `before()` hooks keep firing it unchanged.
2. **No false-positive pressure to disable the guard**: by never injecting
   `AUDIT_DB_URL=<container DSN>` into the destructive step, the guard's
   equality check stays meaningful locally (mirrors CI's documented env
   split). A design that trips the guard routinely would train the operator
   to work around it — that's the real risk, and it's designed out.
3. **The script never reads or writes `.env`**, never prints the developer's
   real DSN (it only prints the container DSN it constructed), and makes no
   network egress beyond `docker pull` of the pinned public image.
4. **Lesson applied** ("env-var *set* is not a safety gate"): the new unit
   test asserts the constructed DSN passes `assertDisposableDbUrl` — a
   positive verification wired into `npm test`, so a future edit that changes
   the DSN shape to something the guard rejects (or that starts injecting
   `AUDIT_DB_URL`) fails fast.

## 8. Risk & Trade-off Register

| Risk / trade-off | Assessment |
|---|---|
| **Image pull on first run** (~400MB) | One-time; the CLI prints pull progress via inherited stderr. Not pre-pulled — no hidden state. |
| **Port 5433 conflict** | `docker run` fails loudly; `--port` escape hatch. Not auto-probing free ports — a moving DSN is worse than a clear error. |
| **Docker Desktop/WSL wedge** (fresh memory: 2026-07-16) | Preflight `docker version` with a bounded timeout fails loud + hints at the recovery recipe. The CLI never attempts to repair Docker (GPT's caveat — repair is the operator's job). |
| **Step-sequence drift vs CI** | Largely mechanised (M2 fix): parity test covers image, test-file membership (both directions), and the concurrency flag. Residual: argv-level and intra-known-file ordering drift — accepted; severity is low because the file-membership guard bounds what can silently diverge. |
| **`--keep` leaves a container running** | Next start now fails loud on a running container (exit 3, H2 fix) rather than silently recycling it; `down` is idempotent and is the operator's explicit teardown. Worst case: an idle ~200MB container until `down`. |
| **Concurrent invocations** | Not lock-protected (solo-dev repo, single Docker daemon). The H2 running-container check makes the collision loud instead of destructive — second invocation exits 3 instead of deleting the first's live DB. A cross-process lockfile is deliberately NOT added (over-engineering for one operator; revisit if this ever runs in shared CI). |
| **Deliberately deferred**: consumer-repo sync of this CLI; a `psql` shell mode; golden-fixtures recording mode | No current requirement; extension points exist. |

  empirical-verify doctrine (runtime-asserting tooling must run against one

  Docker absent (preflight exit 2, distinct from suite-failure exit 1).

## Out of Scope (Future)

- **Full argv/env/order parity verification against the CI YAML** (R3-M2,
  deferred): mechanically asserting the workflow's exact run-step commands,
  argument vectors, per-step env split, and step ordering would require
  parsing YAML run-step semantics — a second implementation of the contract
  rather than a guard on it. **Independence rationale**: the plan's
  correctness does not ride on argv-level identity — the destructive-safety
  invariants are enforced by `assertDisposableDbUrl` + the env-deletion
  design (guard-enforced), not by step ordering; the file-membership +
  concurrency-flag + image guards already bound what can silently diverge;
  and a divergence's blast radius is a *local-mirror fidelity* gap, never a
  production-safety gap. Revisit trigger: a real incident where local-green
  → CI-red traces to an untested parity dimension.
- **Cross-process lockfile for concurrent invocations** (from §8): the
  R3-H1 ownership rule makes the race loud-and-safe (one winner, loser
  exits 3, no cross-kill); a lockfile adds state for a solo-operator repo.
  Revisit if this ever runs on shared infrastructure.
- **Consumer-repo sync of this CLI; `psql` shell mode; golden-fixtures
  recording mode** (from §8): no current requirement; extension points
  exist (mode dispatch table, `STEPS` array).
