- **Date**: 2026-06-26
- **Status**: Complete (GPT+Gemini audited; implemented 2026-06-26)
- **Author**: Claude + Louis
- **Scope**: backend (nav-audit lib: verify capture/settle + activation + scorecard degradation; no UI)

> **Target domain**: `nav-audit`. **Scope/stack**: backend · `js-ts`.
> **Origin**: Authenticated v1.4-precursor evaluation on wine-cellar-app. Live findings (#4) land correctly, but the run is **non-deterministic**: in a fresh storageState context the declared primary container `#primary-nav` is present but never populates (app cold-init rate-limit storm), and `--verify` **silently emits authoritative per-persona verdicts** (misplaced/missing) on that incomplete capture — and the activation pass *amplifies* the storm with up to 16 cold-boot re-navigations. App fix is theirs (PR #42); these two are the tool's.

## 1. Context Summary

Two coupled defects on the live-capture seam, both about **capture robustness + honesty**:

**A (highest value) — incomplete captures are reported as authoritative verdicts.** The settle race (`verify.mjs:158` `.every`-over-present) waits for declared containers to populate, but when a declared container is **present-but-empty** and *never* populates (e.g. `#primary-nav` stalling under cold-init), the race just times out at `hydrateMs` and collection proceeds as if the empty container were the truth. `mergeScorecard` then returns `misplaced`/`missing` — a confident verdict on data we *failed to capture*. A scorecard that flips authoritative PASS↔MISPLACED with prod weather, silently, is worse than one that says "primary capture incomplete — unreliable."

**B — the activation pass amplifies the very storm it's reading.** Each activation trigger does `page.goto(url)` (`verify.mjs:215`) — a fresh cold boot — up to `ACTIVATION_CAP=8` per viewport (×2 = 16). On a rate-limited app this worsens the degradation that broke the base capture, and recovered nothing (all 16 clicks failed "not visible" because the cold-boot nav never mounted).

**Code Trace**:
- `scripts/lib/nav/verify.mjs:158-170` — `.every`-over-present settle; on a never-populating present container it just times out and proceeds.
- `scripts/lib/nav/verify.mjs` (collectState + per-state loop) — pushes `liveEvidence` + `statesCollected`; no per-container capture-completeness signal is recorded.
- `scripts/lib/nav/verify.mjs:209-…` — activation loop re-`goto`s the URL per trigger (cold boot ×N); no back-off when the base capture is already degraded.
- `scripts/lib/nav/live-attribution.mjs:105-117` — `mergeScorecard`: `placements.length===0` → `missing` (full coverage) / `unverified` (partial); placements present but none in `requiredInLayer` → `misplaced`. **No notion of "the required layer's container was present-but-empty (uncapturable)."** `STATUS.UNVERIFIED` already exists.
- `scripts/lib/nav/findings.mjs:227,253` — `personaScorecard` → `mergeScorecard(rows, liveAttribution, {statesRequested, statesCollected})`; the conduit for a new `unverifiableLayers` arg.

**Patterns reused vs new**: ~90% reuse. Reuses the settle/collect loop, `mergeScorecard`, `STATUS.UNVERIFIED`, the activation loop. New: a per-container capture-status probe (pure-ish, in-page) + a small aggregation; one new `mergeScorecard` arg; an activation context-reuse + back-off guard.

**Neighbourhood considered**: intra-domain extension of `verify.mjs` + `live-attribution.mjs`; no near-duplicate.

## 1.5 Execution Model

A and B are **largely independent** (the adaptive back-off measures activation health directly, not A's `unverifiableLayers`). They edit **disjoint regions of `verify.mjs`**: A adds a post-collection capture-status computation (after ALL states, incl. activation); B adds the adaptive early-stop to the existing goto-isolation activation loop. `unverifiableLayers` is computed from the FINAL `liveEvidence` regardless of which activation impl produced it, so A works whether B has landed or not. A (capture honesty — the load-bearing fix) lands first and gates B. Within A, detection (a pure `computeCaptureStatus` helper) and degradation (`mergeScorecard`) are one seam — the helper's output IS the scorecard's new input.

## 2. Proposed Architecture

**Key design decisions** (principles from `references/engineering-principles.md`):

1. **A — a required layer with a STALLED (present-but-empty) container, or with ALL containers absent, is `unverifiable` → degrade to `unverified` instead of an authoritative verdict (R1-H1/H4, R3-H1/H3/H4, R3-Gemini2-H2)** (#15, #19, honesty). "Captured" is NOT `childElementCount>0` (a spinner has children, no nav) — a declared container is **captured** iff the collection produced **≥1 placement attributed to it** (a real target-bearing affordance via `collectLiveNav`/`resolveContainer`); `empty` = present, 0 placements; `absent` = never present. The honest signal accounts for **multi-container (responsive) layers (R3-Gemini2-H2)** — "no captured container" is unsound, because a dest could hide in an *uncaptured* container of an otherwise-captured layer, AND it would over-degrade a legitimate responsive variant. So: **a layer ∈ `unverifiableLayers` iff (≥1 of its declared containers is `present-but-empty`) OR (ALL of its declared containers are `absent`)**:
   - **The probe checks VISIBILITY, not just DOM presence (R3-Gemini3-H1)**: a responsive container is often present in the DOM but `display:none` on the wrong viewport (e.g. `#mobile-nav` on desktop) — and the v1.2 hidden-element skip already excludes its hidden children, so it yields no placement. Probing mere presence would falsely flag it as a "stall." So per state a container is `visible-empty` only if it's **present AND visible** (`getComputedStyle(el).display !== 'none'` and a non-zero box) but produced no placement; a present-but-**hidden** container is classed `hidden` (a responsive off-viewport variant, NOT a stall).
   - `visible-empty` (present + visible + 0 placements) = a **definite stall** (it rendered, occupies space, yet has no affordance) → the layer is unverifiable (a dest could be hidden in the stalled container), even if a sibling was captured. The cold-init case.
   - `absent` (never present) OR `hidden` (present, `display:none`) with a **captured sibling** in the same layer = a **legitimate responsive variant** → NOT unverifiable; an `absent` (selector matched nothing) one also emits an advisory "check the selector" warning. But if **every** container of the layer is absent-or-hidden (none captured, none stalled) → the layer was never observable → unverifiable.
   - So `[A captured, B hidden/absent-this-viewport]` → verifiable; `[A captured, B visible-empty]` → unverifiable (stall); `[A visible-empty, B absent]` → unverifiable; `[A absent/hidden, B absent/hidden]` (none captured) → unverifiable.
   - **Computed post-activation, union-consistent (R3-H1/H3)**: aggregate over ALL collected states INCLUDING activation-derived ones, so a collapsed menu that activation opens counts as captured (resolves the "collapsed menus start empty" tension — only a container empty/absent *even after activation* is uncaptured). "Captured in ANY state" matches the union scorecard ("a dest reachable in any state passes"), so cross-state aggregation is consistent by construction.
   - **Join key (R2-H4)**: probe keyed by the declared `navLayers` selector; `placedContainers` = the set of `liveEvidence[].container` values, which ARE the declared selectors (`resolveContainer` returns the matched selector). Exact join: `container === declared selector`.
   - **`mergeScorecard`** (covers pinned AND unpinned intents — R3-Gemini-H3):
     - **Pinned** (`requiredInLayer` set): dest **found** there → `PASS`; dest **not found** there AND `requiredInLayer ∈ unverifiableLayers` → `UNVERIFIED` (+ `stateWarning`); dest not found in a **verifiable** required layer → `misplaced`/`missing` as today.
     - **Unpinned** (`requiredInLayer: null` — reachability only): ≥1 placement → `PASS` (reachable); **no placement** AND `unverifiableLayers` is non-empty → `UNVERIFIED` (the dest could live in an uncaptured layer — we can't assert `missing`); no placement AND every declared layer verifiable (full capture) → `missing` (full coverage) / `unverified` (partial coverage), as today.
     - "missing" therefore requires BOTH full state coverage AND no unverifiable layer. Diagnostics: `captureStatus` per container (`captured`/`empty`/`absent`) is reported; an `absent` declared container emits a "selector matched nothing — check the contract" advisory.
   - **Output shape**: `unverifiableLayers` is a JSON **array** (R1-H3, never a `Set`); `mergeScorecard` normalises an array-or-Set arg. `captureStatus` is **report-only diagnostic, NOT persisted** in v1.4 (the persisted contract is `unverifiableLayers`; a capture-confidence dashboard visual is deferred — R3-H2).
   - **Band-aid**: bump `hydrateMs` and hope. **Over-built**: a retry/backoff capture loop. **Chosen**: tie verifiability to the evidence we already collect, and degrade any unobservable required layer — present-empty or absent — to `unverified`.

2. **B — keep per-trigger `goto` ISOLATION, bound the storm with ADAPTIVE early-stop (R3-Gemini2-H1)** (#16, #17 don't-amplify-load). The audit ruled out a "warm context (no restore)" — it creates an obscuring trap: a successfully-opened menu can cover the *next* trigger → not-actionable → throw → a chain of false failures → false abort. And a deterministic restore (toggle-close) is flaky. The robust answer that still fixes the storm is the **adaptive early-stop alone**, layered on the existing `goto`-per-trigger isolation:
   - **Per-trigger isolation via `goto` (existing, kept)**: `page.goto(url) → settle → click(trigger) → if url unchanged: collectState(<viewport>+aN); else discard (the trigger navigated, not a menu open)`. Each trigger starts from a clean base — no obscuring, no leakage, no flaky restore. (A `pushState` route change counts as "navigated" → discarded, correct: a route-changing control isn't a menu toggle — R3-Gemini2-M1.)
   - **Adaptive early-stop bounds the cold boots (the actual storm fix)**: on a HEALTHY app the per-trigger `goto`s are harmless; on a DEGRADED app the **adaptive stop caps them** — after `ACTIVATION_FAIL_STOP=3` consecutive click-throws, abort. So the 16-cold-boot amplification becomes ≤ (successes + 3) — bounded exactly at the point the app proves degraded. The user's "reuse one warm context" goal (don't DDoS the nav) is met by the cap, without the warm-context trap.
   - **Adaptive early-stop, NOT a blanket skip (R1-H2)**: a collapsed menu is *expected* present-but-empty — activation is exactly what populates it, so skipping activation because `unverifiableLayers` is non-empty would defeat the feature. Instead, measure activation health directly: if the **first `ACTIVATION_FAIL_STOP` (=3) consecutive** triggers fail (not actionable / not visible — the cold-init/stall signature), STOP the remaining activations with a warning ("activation aborted — N consecutive triggers unresponsive; app likely degraded"). A healthy app where menus open never trips it; a stalled app stops after 3, not 16.
   - **Band-aid**: lower `ACTIVATION_CAP`. **Over-built**: a token-bucket rate-limiter modelling the app. **Chosen**: stop cold-booting, and stop *early* when activation is provably not working — without blanket-disabling the feature on a normal collapsed menu.

## 6. Sustainability Notes

- **Assumption**: a present-but-empty declared container after the full window means "couldn't capture," not "intentionally empty." For nav containers (declared in `navLayers` as places affordances live) this holds; an intentionally-empty declared nav container is a contract error worth surfacing anyway.
- **Forward seam**: `unverifiableLayers` (persisted, additive in the verify-result) is what makes the dashboard degrade to `unverified` instead of a misleading verdict; a future capture-confidence *visual* can read the report-only `captureStatus` diagnostic.

## 8. Risk & Trade-off Register

- **A risk — a legitimately-empty declared nav container is flagged incomplete.** Acceptable/desirable: a declared `navLayers` container that's persistently empty is either a capture failure OR a contract pointing at the wrong selector — both warrant the `unverified` + warning rather than a confident verdict.
- **A risk — partial-state interaction.** `unverifiableLayers` is computed across collected states with the existing rule "captured in ANY state wins"; a container populated on mobile but empty on desktop is **captured** (we saw it), not incomplete. Correct — we have real evidence.
- **B — per-trigger `goto` isolation retained, not a warm context** (R3-Gemini2-H1). The audit ruled out warm-no-restore (an open menu obscures the next trigger → false-abort) and toggle-close (flaky). `goto`-per-trigger gives clean isolation; the **adaptive early-stop** is what bounds the cold-boot storm (≤ successes+3 on a degraded app), so isolation and storm-safety are both satisfied.
- **B trade-off — adaptive failure classification (R2-M2)**: a "not actionable/not visible" trigger is *counted* as a stall signal; a genuinely viewport-hidden discovered trigger could in principle contribute to the 3-consecutive count. Consequence is **graceful, not wrong**: a false early-stop just yields fewer activation states (the base + already-succeeded activations stand); the counter resets on any success, so it only fires when 3 *in a row* fail — the real stall signature. Accepted over a heavier viewport-vs-stall classifier.
- **Cluster A files now include `schema.mjs` + `collect-nav.mjs`** (R2-H5) — persisting `unverifiableLayers` so the dashboard degrades identically; both are within the capture-honesty seam.
- **Deliberately deferred**: a capture-confidence dashboard *visual* (the data now persists; the panel is additive later); any app-side rate-limit modelling (PR #42 is the app's fix); a retry-capture budget (over-built).
