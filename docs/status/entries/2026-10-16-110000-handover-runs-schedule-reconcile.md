## 2026-10-16 — fleet handover runs the schedule-reconcile registry flow first (PR #268)

**Why.** Scheduled-task schedules are stored per Claude account; task prompts are shared on disk. With two accounts alternating weekly, a task created on one never fired on the other. The fix outside the repo is `scheduled-tasks/registry.json` as the source of truth plus a daily `schedule-reconcile` task. Its one manual step (create it once on an account that lacks it) now rides on `fleet handover`, so every coordinator using the synced skill (CES, WCA, STO) gets it.

- **Receive** (`receiveFollowUps`, `reconcileStep` in `scripts/lib/fleet/handover.mjs`; `readScheduleReconcile` in `handover-tasks.mjs`): when `scheduled-tasks/schedule-reconcile/SKILL.md` exists under the destination config root, the FIRST follow-up is the registry step. It says to create `schedule-reconcile` from its SKILL.md if `list_scheduled_tasks` lacks it (cron from `registry.json`), run it, read its one-line report, and never hand-recreate a task the registry covers. The `scheduled-tasks` follow-up names only the uncovered ids. The text's task section prints the reconcile line ahead of the `missing:`/`EXPORT` lines.
- **Unusable registry**: unreadable JSON, no `tasks` array, an entry with no string id, no `schedule-reconcile` entry, or no string cron on it is reported as `registryError` and routed to "fix the registry first". It is never read as a schedule or as coverage.
- **Prepare** (`handover-render.mjs`): BEFORE YOU RELAUNCH says hand-made tasks are adopted on the next daily run, and names `run_scheduled_task schedule-reconcile` to adopt them now. The coordination prompt no longer picks a flow from the source root; it states both and defers to receive's first follow-up, since receive reads the destination root.
- **Docs**: `skills/fleet/references/handover.md` documents the registry flow and the per-task fallback; SKILL.md untouched.
